## Log

- **2026-09-29**: **The Swift rules layer exists, written without Xcode.** SwiftPM builds and tests on the Command Line Tools alone — Xcode supplies the iOS SDK, simulator and bundling, none of which pure logic needs — so `app/BinderSwapCore` now holds the collection model, set gaps, wish list, tradeables, matching, fair-trade suggestion, plan gates and CSV/text export, with **no UIKit, SwiftUI or iOS SDK**. It passes the **same** `spec/vectors/*.json` as the Python reference: 8 tests, all green. Verified by sabotage rather than by passing — dropping the `keep` flag from tradeables and inverting the needs-before-wants ordering each fail the vector that covers them, so the tests demonstrably exercise the logic. New `core-tests` workflow runs it on macOS (the repo is public, so those minutes are free), triggered by `app/**` *and* `spec/vectors/**` so a vector change is seen by both implementations. This is the highest-risk correctness surface in the product — a recognition miss costs one swipe, a trading-rule bug silently corrupts an inventory — and it is now doubled up.
- **2026-09-29**: **Local-first broke the permanent profile QR, and it is now fixed rather than quietly inconsistent.** Two QR mechanisms existed and they fare differently. The *session* QR (in-person swap) is unaffected — it carries a session id, an ephemeral key and a transport hint, never list contents, so it was always a device-to-device handshake. The *permanent profile* QR was specified to point at **live server-side lists**, which local-first removes: we no longer hold anyone's lists to serve. Revised to a **published snapshot**: the user taps publish, we store the for-trade and want lists only (never the collection, values or history), the handle stays permanent so a printed code never dies, and the snapshot is dated, expiring and revocable. Also corrected the §6.5 promise, which said the cloud "stores no wish lists" — untrue the moment anyone publishes. The honest version is "nothing you did not deliberately publish, and only the two lists you chose to show." Same mechanism as the deferred wish-list deep link, so building publish once serves both.
- **2026-09-29**: **Spec restructured around local-first.** Collections never leave the device; the cloud is read-only reference data (catalogue, prices, index packs) plus a relay. That removes the user database entirely, which removes the row-level-security trap that was the easiest way to leak everything, and removes most COPPA/GDPR obligation — those attach to *holding* a child's data, and we hold none. Backup is to the **user's own iCloud Drive**, Premium only, so it costs nothing to run and there is nothing to breach. Children need no account at all: a child device inherits Premium through Family Sharing, the collection is local, trades are in person. Pricing settled at $9.99/mo or $79.99/yr (33% off annual, which matters because trading is seasonal), no lifetime tier. Free is 200 cards, unlimited binders, **no values shown at all** — a stale price in a trading app is worse than none, because someone trades on it and blames us. Conversion rests on match counts that recur, not on a storage wall that fires once.
- **2026-09-29**: Price cache built for the **whole catalogue**: 34,739 cards, 30,790 priced, 92,752 rows, 0 errors after one retry sweep. Final coverage EN 0.962 / JA 0.767, which **supersedes** the n=440 sample reported earlier today (EN 0.964 / JA 0.800) — the sample was directionally right and slightly optimistic on Japanese. TCGplayer's Japanese coverage is exactly 0.000 across all 13,448 JA cards, not merely low, so the EUR decision is structural rather than a threshold call.
- **2026-09-29 (autonomous run, later)**: **A page corpus built from real card art.** Every page test in the repo ran on procedurally generated fake cards, which share nothing with a real card that matters -- not art, not frame, not printed number -- so their numbers were about the generator. `binderswap.realpages` renders the existing simulated photo (plastic pockets, perspective, sleeve glare, noise) around real downloaded images and writes a `labels.json` that `recognition.eval` already reads. 40 pages / 336 pockets / 309 cards:
  layout **1.000**, top-1 **0.977**, top-4 **0.994**, empty-pocket 0.889, false-empty **0**, 2.9 s/page. Auto-confirm at threshold **0.7 gives precision 1.000 at coverage 0.951**, against the SPEC 5.4 bar of >=0.995 precision at >=0.70 coverage.
  **This is a ceiling, not the answer.** The cards are the same reference images the index was built from, degraded by *our* model, so it measures whether the recogniser can recover its own references under degradation we invented. It cannot tell us the degradation model resembles a phone photo. Real accuracy still needs #2. What it does give that no scraped image can is ground truth for identity *and* geometry, over any number of pages and layouts -- which is what the parked segmentation work needs.
  **On sourcing binder photos elsewhere:** eBay's robots.txt prohibits automated access without express permission and names LLM-driven bots specifically, so that is out. Openverse (CC-licensed) returns ~240 loosely matching images, mostly non-commercial licences and none labelled. Neither is worth having next to a generator with exact ground truth.
  **This also reframes the segmentation finding, and downgrades it.** On these pages -- a real binder page lying on a table, photographed at an angle, with glare -- `locate_page` gets layout **1.000** and the pipeline reaches top-1 0.977 with no change at all. The 0.611 failure was specific to the cardbinderideas composites, which are not photographs of binders: they are posters with a title bar and a watermark, and `content_bounds` was including those bands. `locate_page` fails when there is no page to find, which a binder photo always has. So the parked branch is likely solving a problem the product does not have, and segmentation drops below number reading in priority. Worth re-testing once real photos land, since a real photo also contains hands, table clutter and captions that these renders do not.
  Weakest number is empty-pocket detection at 0.889. False-empty is 0, so it errs toward calling an empty pocket a card, which is the safe direction -- the user dismisses it rather than losing a card silently.
- **2026-09-29 (autonomous run)**: **Latency.** A 9-card page took 10.18s. Measured by switch in one process: OCR off 0.20s, ORB off 10.09s -- OCR was 10.0s of it, and the profile put 9.4s in `select.poll` across 54 `fork_exec` calls (six Tesseract subprocesses per card), i.e. process spawn, not recognition. Reading the pockets concurrently gives **3.82s**, identical output. Still above the <1s target.
  **First measurement of Tesseract on real number bands** (n=150 EN cards, exact number *and* total): **0.767 on clean scans, 0.487 under mild degradation.** PSM 7 scores 0.007/0.000 -- two of the six subprocesses earn nothing. Dropping PSM 7 took the page to **1.22s**, 8.3x faster than where it started, at a cost of 1 card in 200 at mild degradation and 0 in 200 clean or heavy (n=200 per severity). Since the number band is the primary discriminator for reprints (~97% of the near-duplicate tail) and the only per-card identity on puzzle cards, <0.5 under mild degradation is the strongest argument yet for a purpose-built reader over general OCR.
  *Retracted from earlier in this run*: figures of 0.033/0.060 for the same measurement. They came from my harness forcing `canonical()` before cropping the band, shrinking it from 99x600 to 41x240; `read_number` only does that below 400px width. The clean-image sanity check is what caught it.
  **Segmentation: no fix, and the two corpora conflict.** Four variants measured on both (synthetic labelled pages / real composites, cards top-1): main 0.920/0.611; fitted grid in `slots_for` only 0.120/0.611; fitted grid in outline scoring only 0.880/0.500; both 0.000/**1.000**. The real-composite gain comes from outline *selection*, not from the fitted grid, and 1.000 needs both changes -- the configuration that fixes real destroys synthetic. A coverage-floor constraint was swept (0.5-0.8) and made synthetic monotonically worse (0.160 -> 0.080). A page-outline override margin was swept (0.0-1.0) and did nothing, because it scaled a baseline that is often negative. Neither corpus is a photograph, so **this should not be tuned further until #2 lands.**
- **2026-09-29**: **Segmentation, not the embedder, is the bottleneck.** Tested on real binder composites from cardbinderideas.com (digital renders built from the same TCGdex art we hold, so they cannot measure accuracy -- but they do test geometry, which synthetic pages never have). Crops taken from the true pocket area recognise **18/18**; the pipeline's own crops get **12/18**. Root cause: `slots_for` stretches the grid across whatever `content_bounds` returns, and `content_bounds` is a soft cardness threshold that a title bar, a watermark or any colourful margin defeats -- it returned the entire image, so the grid covered title + cards + watermark and every pocket was displaced. A plain uniform grid on the right region gives 9/9 on the page traced end to end, with no per-card contours, which is also what puzzle cards require. A fix attempt that searches for the grid placement reaches 18/18 on composites but regresses five synthetic-page tests; parked on branch `segmentation-grid-fit`. **Not fixed on main.** Also open: `recognize` takes ~14s on a 9-card page (segmentation is only 0.16s of that; the rest is OCR + ORB), against a <1s target.

This makes number-band reading the primary discriminator for hard cases, not a supporting signal. Numbers are an upper bound: clean art, synthetic degradation, no OCR/ORB/priors.
